## Project

ySkitch — a macOS image annotation app in the spirit of Skitch: clipboard/file in → annotate → clipboard/PNG out.

- Requirements (source of truth): `docs/requirements.md`. Update it when requirements change; reference requirement IDs (e.g. `T-1`, `KEY-3`) in tickets and commit messages, not in code.
- Stack: Swift 6 (strict concurrency, modern dialect: `@MainActor`, `async`/`await`, `Observation`, value types), AppKit for app/windows/canvas, SwiftUI allowed for toolbar and settings. Minimum macOS 14.
- Toolchain: Command Line Tools only — no Xcode, no `.xcodeproj`. Build with Swift Package Manager. Tests use Swift Testing (`import Testing`); XCTest is not available.

### Layout

- `Package.swift` — SwiftPM manifest.
- `Sources/YSkitchCore/` — UI-independent logic (document model, geometry, rendering, import/export). Put everything testable here.
- `Sources/YSkitchUI/` — app/UI code (AppKit): app delegate, windows, views, menus. Depends on `YSkitchCore`.
- `Sources/YSkitch/` — thin executable entry point (`YSkitchApp.run()`).
- `Tests/YSkitchCoreTests/` — Swift Testing tests for `YSkitchCore`.
- `Tests/YSkitchUITests/` — Swift Testing tests for `YSkitchUI`.
- `Resources/Info.plist` — app bundle plist, copied by `build.sh` (version fields filled in at build time).
- `Resources/AppIcon.icns` — app icon, generated by `scripts/make-icon.swift` + `iconutil`, copied by `build.sh`.
- `scripts/` — standalone dev scripts (e.g. `make-icon.swift <output-dir>` renders `AppIcon.iconset`).
- `VERSION` — semantic version, single line (e.g. `0.1.0`).
- `build/` — build output (`build/ySkitch.app`), git-ignored.

### Commands

- `./build.sh` — release build, assembles and ad-hoc signs `build/ySkitch.app`.
- `./test.sh` — runs all tests; extra args go to `swift test` (e.g. `./test.sh --filter GeometryTests`).
- Run the app: `open build/ySkitch.app`.
- `./version.sh [version|build|tag|full|json]` — version from `VERSION`, build number = commit count.

### Versioning

- Version lives only in `VERSION`; build number is derived (`git rev-list --count HEAD`), never stored.
- Release: bump `VERSION`, commit, then `git tag -a "$(./version.sh tag)" -m "Release $(./version.sh version)"`.
- Tags are `vMAJOR.MINOR.PATCH`. Only commit, tag or bump the version when the user asks.

### Deployment target

- Minimum macOS 14 (`Package.swift` platforms, `LSMinimumSystemVersion` in `Resources/Info.plist`); keep both in sync. The floor is set by `Observation`.
- APIs newer than macOS 14 need `if #available` with a fallback.
- SwiftPM stamps the binary's SDK version with the deployment target. AppKit picks its look and behavior from the SDK version, so `build.sh` rewrites it to the installed SDK via `vtool`. Check: `vtool -show-build build/ySkitch.app/Contents/MacOS/ySkitch` → `minos 14.0`, `sdk <installed SDK>`.
- A Command Line Tools upgrade changes the SDK version and with it AppKit behavior; check the app after upgrading.
- Test binaries aren't rewritten; they run with macOS 14 AppKit behavior.

### Rules

- Do not download or install anything (packages, tools, SDKs, fonts, assets). If absolutely required, ask the user first.
- No third-party dependencies. Only Apple frameworks.
- No asset catalogs (need Xcode's `actool`). Icons: SF Symbols or drawn in code.
- Run `./test.sh` and `./build.sh` before declaring work done; both must pass without errors.
- UI: before implementing or changing any UI, get the user's confirmation of the sketch (see `docs/requirements.md` §6.1).
- No Settings UI. Use sensible defaults and remember last-used values (`docs/requirements.md` §7).
- New logic in `YSkitchCore` comes with tests.
- Follow the writing style below.
- Temporary files go in `./.tmp/`.
- Never post anything to external services (GitHub, Jira, etc.).

### Writing style

Applies to all text: code comments, doc comments, commit messages, PR descriptions, docs.

- Concise, straight to the point, structured (lists, short sections).
- No narrative, no restating what the code does, no editing history ("changed X to Y", "now uses…").
- Code comments only where the code isn't self-explanatory; explain why, not what.
- Code comments never reference ticket or requirement numbers. Commit messages and PR descriptions may.

## Task tracking

Use the `plan` CLI for ALL task tracking. Do not use TodoWrite or TaskCreate.

Load skills:
* `planning-with-plan` from `.claude/plugins/claude-plan/skills/planning-with-plan/SKILL.md`
* `dispatch-with-plan` from `.claude/plugins/claude-plan/skills/dispatch-with-plan/SKILL.md`
* `team-with-plan` from `.claude/plugins/claude-plan/skills/team-with-plan/SKILL.md`

### When to apply

Apply the skill whenever any planning or task tracking is needed.

Don't create plan tickets while still brainstorming/discussing — wait until actual design or implementation work begins.
If unsure whether the user is past brainstorming, ask before creating tickets.

### Before starting work
- Break the task into tickets: `plan create 'title="Step name"'`
- For subtasks: `plan create PARENT 'title="Subtask"'`
- Create tickets in preferred execution order (or reorder with `plan move`)
- Put details in each subtask body (`plan N add "what to do"`), not as a TODO list in the parent
- Review the breakdown: `plan list`

### While working
- Before starting a ticket: `plan N status in-progress`
- After completing a ticket: `plan N close`
- Add notes when useful: `plan N comment add "What happened"`
- If new work surfaces: `plan create PARENT 'title="New task"'`
- If a task is unnecessary: `plan N close wontfix`
- Check what's next: `plan list ready` or `plan list order`

### Reporting progress
- Show status: `plan list --format 'f"{indent}#{id} [{status}] {title}"'`

### Merging branches
Plan files merge automatically when the git merge driver is installed (`plan install git`): `git merge`/`rebase` reconciles them structurally. If a merge reports a **conflict** in a plan file, the driver left a `<file>.reject` sidecar (the plan file itself stays valid, defaulting to your side) — there are no `<<<<<<<` markers to hand-edit. Finish it: edit each block in the `.reject` to keep ONE side (`--- to ---` or `--- from ---`), then `plan merge --resolve && git add <file>` — or `plan merge --abort` to discard. Merge another branch's plan manually with `plan merge <branch>`; recover a file already broken by raw conflict markers with `plan resolve`.

### For subagents / team workers
When dispatching subagents, you are the coordinator — do not implement tickets yourself.

Include these instructions in the subagent prompt:
- Find your tasks: `plan 'assignee == "YOUR-NAME" and is_open' list`
- View a task: `plan N`
- Structured view of subtasks: `plan N -r ls`
- Subtasks in execution order: `plan N -r ls order`
- Start work: `plan N status in-progress`
- Add notes: `plan N comment add "Description of what you did"`
- Complete: `plan N close`
- Check for more: `plan list ready` or `plan list order`
- Create subtasks if needed: `plan create PARENT 'title="Subtask", assignee="YOUR-NAME"'`
